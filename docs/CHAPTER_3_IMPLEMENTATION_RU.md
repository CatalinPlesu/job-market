# Глава 3. Реализация системы

## Введение

В данной главе рассматриваются ключевые технические решения, принятые при разработке системы автоматического анализа и классификации вакансий с рынка труда Республики Молдова. Описываются причины выбора конкретных технологий, возникшие проблемы и пути их решения, а также перспективы дальнейшего развития проекта.

## 3.1. Выбор технологического стека

### 3.1.1. Python как язык прототипирования

При выборе языка программирования для реализации системы было принято решение использовать **Python**. Это решение было обусловлено следующими факторами:

**Преимущества для прототипирования:**
- Высокая скорость разработки и простота синтаксиса
- Богатая экосистема библиотек для web scraping (BeautifulSoup4, requests, aiohttp)
- Отличная поддержка работы с данными (pandas, SQLAlchemy)
- Обширные возможности для интеграции с API машинного обучения
- Низкий порог входа для прототипирования идей

**Ключевые Python-библиотеки, использованные в проекте:**

**Backend (Scraper):**
- **SQLAlchemy** - ORM для работы с базами данных SQLite (scrape.db и data.db)
- **BeautifulSoup4** - парсинг HTML-документов и извлечение данных
- **requests** - синхронные HTTP-запросы для получения веб-страниц
- **aiohttp** - асинхронные HTTP-запросы для параллельного scraping
- **openai** - интеграция с LLM API для структурирования данных
- **pandas** - обработка и анализ данных (опционально для аналитики)
- **rich** - красивый терминальный интерфейс и логирование

**База данных:**
- **SQLite** - легковесная реляционная база данных, используемая как на стороне scraper (для хранения сырых и обработанных данных), так и на стороне клиента (в браузере через SQL.js)
- Две базы данных: `scrape.db` (сырые данные) и `data.db` (нормализованные данные)

**Инфраструктура:**
- **schedule** - планирование автоматических запусков scraping
- **python-dotenv** - управление переменными окружения

**Выявленные недостатки в процессе разработки:**

По мере роста проекта проявились определенные ограничения использования Python:

1. **Отсутствие статической типизации:** При расширении кодовой базы отсутствие строгой типизации усложняет поддержку и рефакторинг кода. Ошибки типов обнаруживаются только во время выполнения, что увеличивает время отладки.

2. **Сложность поддержки:** С ростом числа модулей и взаимосвязей между ними становится труднее отслеживать зависимости и гарантировать корректность работы системы.

3. **Производительность:** Для некоторых операций, особенно при обработке больших объемов данных, производительность Python оказывается недостаточной по сравнению со статически типизированными языками.

**Альтернативные решения:**

Для будущих версий или масштабных проектов более целесообразным было бы использование:
- **TypeScript/JavaScript (Node.js)** для backend - статическая типизация, высокая производительность, единая экосистема с frontend
- **Go** - статическая типизация, высокая производительность, простое развертывание
- **Rust** - максимальная производительность и безопасность памяти

**Текущее состояние:**

Несмотря на выявленные недостатки, для данного прототипа Python остается оптимальным выбором. Система функционирует стабильно и эффективно решает поставленные задачи. В случае необходимости миграции на другой язык, модульная архитектура облегчит этот процесс.

### 3.1.2. Выбор подхода к обработке данных: LLM против традиционного Machine Learning

Одним из ключевых архитектурных решений стал выбор между традиционными методами обработки естественного языка (NLP) с машинным обучением и использованием больших языковых моделей (LLM).

#### Специфика рынка труда Молдовы

Рынок труда Республики Молдова обладает уникальной особенностью - **многоязычностью**. Вакансии публикуются на трех языках:
- **Румынский** - государственный язык
- **Русский** - широко используется в бизнес-среде
- **Английский** - для международных компаний и IT-сектора

Эта многоязычность создает серьезные проблемы для традиционных подходов NLP:

**Проблемы традиционного подхода:**

1. **Сегрегация данных:** Классические модели ML требуют обучения на данных каждого языка отдельно, что приводит к:
   - Разделению датасета на три независимых подмножества
   - Усложнению сравнительного анализа вакансий на разных языках
   - Необходимости поддержки трех различных моделей

2. **Проблема перевода:** Использование API автоматического перевода для унификации языка рассматривалось как возможное решение, но имеет существенные недостатки:
   - **Высокая стоимость:** Сервисы перевода (например, Google Translate API) стоят около $20 за 1 миллион символов
   - **Потеря контекста:** Автоматический перевод может исказить технические термины и специфическую лексику вакансий
   - **Дополнительная задержка:** Необходимость дополнительного API-запроса для каждого документа

3. **Сложность извлечения структурированных данных:** Традиционные NLP-модели требуют:
   - Создания отдельных классификаторов для каждого поля (должность, индустрия, навыки)
   - Обучения NER (Named Entity Recognition) моделей для извлечения сущностей
   - Постобработки и нормализации результатов

#### Преимущества LLM-подхода

Использование больших языковых моделей решает все перечисленные проблемы:

**1. Естественная многоязычность:**
- Современные LLM обучены на многоязычных корпусах
- Единая модель обрабатывает тексты на румынском, русском и английском языках без дополнительной настройки
- Сохраняется контекст и семантика независимо от языка

**2. Экономическая эффективность:**

Для данного проекта использовалась модель **"mistral-small-3.2-24b-instruct"** со следующими ценами:
- **Input (входящие токены):** $0.06 за 1 миллион токенов
- **Output (исходящие токены):** $0.18 за 1 миллион токенов
- **Средняя стоимость:** ~$0.12 за 1 миллион токенов
- **Эквивалент в символах:** 1 токен ≈ 4 символа, т.е. ~4 миллиона символов на $0.12

**Сравнение стоимости:**
- **API перевода:** $20 за 1M символов
- **LLM обработка:** $0.03 за 1M символов (в среднем)
- **Экономия:** более чем в 650 раз дешевле

**Реальные результаты:**
- **Обработано:** 16,700+ вакансий
- **Затрачено:** ~$7 на API-кредиты
- **Результат:** Конвертация сырого текста в структурированный JSON с 30+ полями

**3. Комплексное извлечение данных:**

LLM выполняет несколько задач одновременно в рамках одного запроса:
- Извлечение структурированной информации (должность, компания, зарплата)
- Классификация по отраслям и категориям
- Нормализация названий должностей и навыков
- Парсинг зарплатных диапазонов с учетом различных форматов
- Извлечение технических навыков, soft skills, требований к образованию

**4. Понимание контекста:**

LLM способны:
- Интерпретировать неструктурированные описания
- Распознавать синонимы и вариации терминов
- Делать логические выводы из неявной информации
- Обрабатывать опечатки и нестандартное форматирование

#### Альтернативные подходы

Были рассмотрены следующие альтернативы:

**1. Традиционный NLP + ML:**
- Требует больше времени на разработку и обучение моделей
- Необходима значительная размеченная выборка для каждого языка
- Сложность интеграции и поддержки множества специализированных моделей

**2. Перевод + NLP:**
- Высокие затраты на API перевода
- Потеря качества из-за ошибок перевода
- Дополнительная латентность

**3. Мультилингвальные BERT-модели:**
- Требуют обучения на специфичных для домена данных
- Ограниченная длина контекста (512 токенов)
- Необходимость отдельных моделей для каждой задачи извлечения

#### Выводы

Выбор LLM-подхода оказался оптимальным решением для данного проекта благодаря:
- Естественной поддержке многоязычности
- Высокой экономической эффективности
- Качественному извлечению структурированных данных
- Простоте интеграции и поддержки

Такой подход позволил создать единую систему обработки, которая обеспечивает высокое качество результатов при минимальных затратах на разработку и эксплуатацию.

## 3.2. Архитектурные решения для минимизации затрат

### 3.2.1. Статическое веб-приложение на GitHub Pages

Для снижения операционных расходов и упрощения развертывания было принято решение о размещении системы как **статического веб-приложения** на GitHub Pages.

#### Преимущества статического подхода

**1. Нулевые затраты на хостинг:**
- GitHub Pages предоставляет бесплатный хостинг для статических сайтов
- Отсутствие необходимости в аренде серверов или облачных инстансов
- Автоматическое масштабирование и CDN от GitHub

**2. Отсутствие backend-сервера:**
- Не требуется серверная инфраструктура
- Снижение сложности развертывания и поддержки
- Повышение надежности (нет единой точки отказа)

**3. Простота обновления:**
- Автоматическое развертывание через Git push
- Версионирование через Git
- Откат к предыдущим версиям в несколько команд

#### Техническое решение: SQLite в браузере

Ключевой технологией, позволившей реализовать статическое приложение с полнофункциональной базой данных, стало использование **SQL.js** - порта SQLite для JavaScript через WebAssembly.

**Архитектура:**
```
┌─────────────────────────────────────────┐
│         GitHub Pages (статика)          │
│  ┌───────────────────────────────────┐  │
│  │   HTML + CSS + JavaScript (SPA)   │  │
│  └───────────────────────────────────┘  │
│  ┌───────────────────────────────────┐  │
│  │   SQL.js (SQLite WebAssembly)     │  │
│  └───────────────────────────────────┘  │
│  ┌───────────────────────────────────┐  │
│  │   База данных (data.db - SQLite)  │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
              ↓ Download
         Браузер клиента
```

**Процесс работы:**
1. Пользователь открывает веб-страницу
2. Браузер загружает файл базы данных SQLite (data.db)
3. SQL.js загружает базу данных в память браузера
4. Все SQL-запросы выполняются локально на клиенте
5. Результаты отображаются через Mithril.js фреймворк

**Frontend-библиотеки:**

- **Mithril.js** - легковесный JavaScript фреймворк для построения SPA
  - **Простота:** Проще в изучении и использовании, чем React
  - **Размер:** ~10KB gzipped против ~40KB у React
  - **Производительность:** Быстрый virtual DOM с минимальными overhead
  - **API:** Минималистичный и понятный API без сложных концепций
  - Идеален для небольших и средних проектов, где не нужна сложная экосистема React
  
- **SQL.js** - порт SQLite в JavaScript через WebAssembly
  - Позволяет выполнять SQL-запросы прямо в браузере
  - Полная совместимость с SQLite синтаксисом
  
- **Chart.js** - визуализация данных (графики, диаграммы)
  - Интерактивные графики для аналитики
  - Поддержка множественных типов визуализаций
  
- **DaisyUI + Tailwind CSS** - UI компоненты и стилизация
  - Готовые компоненты интерфейса
  - Утилитарный подход к стилизации
  - Поддержка темной/светлой темы

**Архитектурное преимущество Mithril.js:**

В отличие от React, Mithril не требует сложной настройки build system, JSX транспиляции или большого количества зависимостей. Для статического сайта, загружаемого с CDN, это критично - минимальный размер бандла означает быструю загрузку даже при медленном интернете. Простота API позволяет сосредоточиться на логике приложения, а не на изучении фреймворка.

#### Выявленные ограничения

По мере роста базы данных проявились серьезные проблемы с производительностью:

**1. Размер базы данных:**
- Текущий размер: более 100MB (после обработки 16,700+ вакансий)
- Тенденция: постоянный рост с добавлением новых данных
- Проблема: браузер должен загрузить весь файл перед началом работы

**2. Производительность на клиенте:**

**Десктопные компьютеры:**
- Загрузка базы данных: 5-15 секунд (в зависимости от скорости интернета)
- Инициализация SQL.js: 2-5 секунд
- Выполнение запросов: приемлемая скорость для простых запросов
- Сложные JOIN-запросы: могут занимать несколько секунд

**Мобильные устройства:**
- **Значительно медленнее** из-за:
  - Ограниченной оперативной памяти
  - Более медленных процессоров
  - Медленного мобильного интернета
- Загрузка может занимать 30+ секунд
- Риск сбоев при нехватке памяти на старых устройствах
- Неприемлемая производительность для сложных запросов

**3. Ограничения браузера:**
- Лимиты на размер загружаемых файлов
- Ограничения памяти (особенно на мобильных устройствах)
- Невозможность инкрементальной загрузки данных

**4. Проблемы масштабируемости:**
- Каждый запрос пользователя загружает всю базу данных
- Увеличение трафика GitHub Pages
- Нет возможности кэширования на уровне данных

#### Временное решение: Custom Database Server

Для частичного решения проблемы был разработан **Custom Database Server** (`db_server.py`):

**Характеристики:**
- Standalone Python сервер (без внешних зависимостей)
- Поддержка загрузки/скачивания баз данных
- Интеграция с Caddy для HTTPS
- Решает проблемы CORS

**Ограничения:**
- База данных все равно загружается целиком в браузер
- Не решает проблему производительности на клиенте
- Требует дополнительной инфраструктуры

#### Выводы по статическому подходу

**Преимущества:**
- ✅ Нулевые операционные расходы
- ✅ Простота развертывания
- ✅ Высокая надежность
- ✅ Подходит для MVP и демонстрации концепции

**Недостатки:**
- ❌ Низкая производительность на мобильных устройствах
- ❌ Долгая начальная загрузка
- ❌ Проблемы масштабируемости при росте данных
- ❌ Ограниченные возможности для сложных аналитических запросов

**Вывод:** Статический подход оправдал себя для прототипа и демонстрации концепции, но при дальнейшем развитии проекта необходим переход на полноценный backend.

## 3.3. Перспективы развития проекта

### 3.3.1. Архитектурные улучшения

#### Миграция на современный backend

**Необходимость:**
- Решение проблем производительности
- Обеспечение масштабируемости
- Улучшение пользовательского опыта

**1. Пагинация и ленивая загрузка:**

- Предзагрузка следующей страницы для плавного UX

**2. Кэширование:**
- Redis для кэширования популярных запросов

**3. Оптимизация запросов:**
- Индексы на часто используемых полях

- Корпоративные клиенты: 1-2 × $99 = $99-198/месяц
- **Итого:** $1,198-1,497/месяц

**Точка безубыточности:** 20-30 premium пользователей

### 3.3.3. Улучшение качества данных

#### RAG (Retrieval-Augmented Generation) для нормализации

**Проблема:**
Разные вакансии могут использовать различные формулировки для одних и тех же концепций:
- "JavaScript Developer" vs "JS Developer" vs "Javascript Engineer"
- "Senior" vs "Lead" vs "Principal"
- "Full-stack" vs "Fullstack" vs "Full Stack"

**Решение через RAG:**

**1. Создание базы знаний:**
- Словарь нормализованных терминов
- Синонимы и вариации названий
- Иерархия навыков и должностей

**2. Векторные представления:**
- Использование embedding моделей (e.g., OpenAI embeddings)
- Хранение в векторной БД (Pinecone, Weaviate, ChromaDB)
- Семантический поиск похожих терминов

**3. Процесс нормализации:**
```
Входной термин → Embedding → 
Семантический поиск → Нормализованный термин
```

**Преимущества:**
- Автоматическая группировка похожих терминов
- Улучшенная точность фильтрации
- Более релевантные результаты поиска
- Снижение дублирования в базе данных

**Пример:**
```
"React.js" + "ReactJS" + "React" → "React"
"Machine Learning" + "ML" + "МО" → "Machine Learning"
```

#### Использование более мощных LLM моделей

**Текущая модель:** mistral-small-3.2-24b-instruct
- Хорошее соотношение цена/качество
- Достаточная точность для большинства задач

**Потенциальные улучшения:**

**1. GPT-4 или Claude 3:**
- Более высокая точность извлечения данных
- Лучшее понимание контекста
- Более последовательная нормализация

**Компромисс:**
- Стоимость: в 5-10 раз выше текущей модели
- Необходимость оценки ROI: улучшится ли качество достаточно для оправдания затрат?

**2. Гибридный подход:**
- Использование дешевой модели для первичной обработки
- Применение мощной модели для сложных или неоднозначных случаев
- ML-классификатор для определения сложности вакансии

**3. Fine-tuning специализированной модели:**
- Обучение на размеченных данных вакансий
- Оптимизация для специфики молдавского рынка труда
- Потенциально лучшее качество при меньшей стоимости

#### Валидация и верификация данных

**1. Автоматическая проверка качества:**
- Детектирование аномалий в зарплатах

## 3.4. Заключение главы

В данной главе были рассмотрены ключевые технические решения, принятые при реализации системы автоматического анализа и классификации вакансий с рынка труда Республики Молдова.

### Основные выводы:

**1. Выбор технологий:**
- Python оказался оптимальным выбором для прототипирования, несмотря на выявленные ограничения при масштабировании
- Использование LLM вместо традиционного NLP решило проблему многоязычности и обеспечило высокое качество извлечения данных при минимальных затратах
- Статический подход к развертыванию позволил минимизировать операционные расходы, но выявил серьезные проблемы с производительностью при росте данных

**2. Экономическая эффективность:**
- LLM-подход оказался в 650+ раз дешевле, чем использование API перевода
- Обработка 16,700+ вакансий обошлась всего в ~$7
- Статический хостинг на GitHub Pages обеспечил нулевые затраты на инфраструктуру

**3. Выявленные ограничения:**
- Отсутствие статической типизации в Python усложняет поддержку при росте проекта
- Загрузка всей базы данных в браузер критически снижает производительность на мобильных устройствах
- Текущая архитектура не масштабируется для коммерческого использования

**4. Перспективы развития:**
- Необходим переход на полноценный backend с PostgreSQL и API
- Требуется стратегия монетизации для обеспечения устойчивого развития
- RAG и более мощные LLM модели могут значительно улучшить качество данных
- Расширение функциональности (рекомендации, предсказания, интеграции) откроет новые возможности для пользователей

### Практическая значимость:

Несмотря на выявленные ограничения, разработанный прототип успешно демонстрирует жизнеспособность концепции автоматического анализа рынка труда с использованием современных технологий машинного обучения. Система уже сейчас предоставляет ценную информацию для соискателей, работодателей и исследователей.

Описанные в данной главе решения и подходы могут служить основой для создания коммерческого продукта или применяться в аналогичных проектах анализа неструктурированных данных в других доменах.
